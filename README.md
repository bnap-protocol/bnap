# BNAP

BNAP is an open protocol for priced and permissioned requests between
machines over HTTP and MCP. This repository holds the specification, the
registry, the test vectors and the conformance suite.

## What the protocol is

A server that wants to be paid, or wants proof of who is calling, answers a
request with HTTP 402 (or an MCP error) and a **signed offer**. The offer
names the price, the action it covers and the schemes the server accepts.
The client sends one **credential** with the retried request: one payment
and any number of attestations. The server checks the credential against
its offer, records each payment as used **once only**, runs the action, and
answers with a **signed receipt**.

- **The socket** is the part every deployment shares: byte layouts (TLV),
  the offer and credential checks, the use and outcome model, receipts and
  the signed manifest an origin publishes at `/.well-known/bnap`.
- **Plugs** are everything else: credential schemes, settlement rails,
  carriers, stores and signers. A registry records what each scheme
  guarantees, so a server decides what it trusts from the registry, not
  from the plug.
- **The default scheme** is `bnap:notes`: blind ecash notes bought over
  Lightning, with change and refunds, so the server does not learn which
  payment funded which request. L402 and MPP (`payment:lightning/charge`)
  fit the same socket, and one Lightning payment admits one action
  whichever scheme presents it.

## Run the conformance suite

The suite needs only Python 3.11 or later, with no packages. Run it from the
repository root. Point the runner at a gate:

```sh
python3 -I conformance/run.py --target https://gate.example --profile server --report out/
```

- `--profile client` only reads the manifest and offers. `server` adds every
  credential path that needs no money. `gateway` adds what a gate in front
  of an application owes it, and needs `--role` routes.
- Paid cases need `--payer cmd:<command>` (for lnd,
  `conformance/payers/lncli-payer.sh`) and a spending cap
  `--max-spend-sat`. Without a payer they are skipped.
- `--allow-http` allows a plain-HTTP target, for test gates only.
- The exit status is 0 when every MUST case of the profile ran and passed,
  1 when one failed or errored, 3 when MUST cases were skipped (the verdict
  then says "incomplete"). Reports land in `out/` as `report.json`,
  `junit.xml` and `report.html`.

To try it without a gate of your own, run the mock gate in one shell and the
runner in another:

```sh
python3 -I conformance/mock_gate.py serve --port 9188
python3 -I conformance/run.py --target http://127.0.0.1:9188 --allow-http --profile server
```

The second command ends with `85 passed, 0 failed` and the verdict
`incomplete: 10 MUST cases not run` (the paid cases, as no payer is given).
[`conformance/README.md`](conformance/README.md) has every option, the
payer contract and the suite's own tests.

## Proposing changes

- **Spec text.** Open an issue first that describes the problem, so the
  design is agreed before text is written. Normative changes update the test
  vectors and the reference encoder in the same pull request. A difference
  found between documents goes into `spec/ERRATA.md`; a provisional answer
  to an open erratum goes into `spec/DECISIONS.md`.
- **Registry.** A new scheme, rail, verifier or carrier is a pull request
  against the TOML files in `registry/`, with a public specification. Run
  `python3 -I registry/validate.py --export` to regenerate the export and
  `python3 -I registry/validate.py --check` to check it. Listing needs test
  vectors, passing conformance results and expert review; see
  [`registry/README.md`](registry/README.md).
- **Questions** about the text go to
  [issues](https://github.com/bnap-protocol/bnap/issues/new/choose).
- **Security problems** in the protocol go through
  [private vulnerability reporting](https://github.com/bnap-protocol/bnap/security/advisories/new),
  never a public issue. See [SECURITY.md](SECURITY.md).

Every commit needs a DCO sign-off (`git commit -s`).
[CONTRIBUTING.md](CONTRIBUTING.md) lists the checks CI runs. Changes are
recorded in [CHANGELOG.md](CHANGELOG.md).
