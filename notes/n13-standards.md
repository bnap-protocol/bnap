## 1. bnap:notes draft-00: the contract downstream nodes build against

The document is normative for the `bnap-scheme-notes` crate, the wallet (`caparra-wallet`), the issuer endpoints in the gate, and the notes test vectors. Section numbers below are of `spec/schemes/bnap-notes-draft-00.md`.

### Wire objects

| Object | Where it lives | Section |
| --- | --- | --- |
| Body | Credential `pay` record, nested type 2. TLV: 0 `inputs` (entry list), 2 `outputs` (entry list), 4 `fund` (UTF-8 quote ID, 1 to 64 bytes) | 3.1 |
| Input entry | 0 `keyset` (33-byte full keyset ID), 2 `amount` (tu64 power of two), 4 `key` (32-byte x-only K), 6 `C` (33-byte point). Inputs sorted by `key`, strictly ascending | 3.2 |
| Output entry | 0 `keyset` (33 bytes, an active keyset), 2 `amount` (tu64 power of two), 4 `blinded` (33-byte B') | 3.3 |
| Witness | Credential `pay` record, nested type 4. TLV: 0 `input_sigs` (64 bytes per input, input order), 2 `fund_sig` (64 bytes). All BIP-340 over the socket Digest | 3.4 |
| Pay entry params | Offer pay entry record 8. TLV: 0 `issuer` URL, 2 `keysets` (entry list: 0 id, 2 input_fee_ppk, 4 active flag), 4 `max_inputs`, 6 `max_outputs` (default 16 each), 8 `max_fund`, 10 `fund_quote` | 5.1, 5.2 |
| fund_quote | 0 quote ID, 2 BOLT11 request, 4 amount, 6 expiry, 8 33-byte NUT-20 pubkey | 5.3 |
| scheme_result | Response record 16. TLV: 0 `signatures` (entry list: 0 index tu64, 2 C' point, 4 DLEQ e, 6 DLEQ s). Omitted when the change is 0. Required records are written even when empty, so the index of output 0 is the present empty record `00 00` (entry stream 105 bytes; 106 for indices 1 to 255); clients read an absent index as 0 (P32) | 7.3 |

Bodies and witnesses are strict: any unknown record, even or odd, any empty record, any input or output entry missing a Required record (an input without `C`, or the empty entry `00`; added in repair round 4) and any non-canonical encoding is BAD\_CREDENTIAL with `bnap:notes/NON_CANONICAL` (3.5). That includes a non-minimal BigSize or tu64 inside them, which draft-00 section 2 read literally would make socket MALFORMED; the socket streams around them keep MALFORMED (2.1, P33). Params follow the even/odd rule, and a client treats a pay entry whose `params`, keyset entry or `fund_quote` lacks a Required record as unusable (5.1).

### What `verify` returns (6.4)

- local IDs: the 33-byte compressed `Y = hash_to_curve(hex(K))` of each input, use model `single`;
- rail references: none, except kind `ln` with the invoice payment hash when the body holds `fund`;
- value: `I + F - fee`, fee = `(sum of input_fee_ppk + 999) div 1000`, checked u64 arithmetic (6.3).

Outputs and quote IDs are not use IDs. `verify` has no side effects and runs the seven checks of 6.2 in order. It reads no use state at all: it checks that a fund quote is paid, never whether it has issued (the RailId commit is the single-use check), and it never consults the signed-output table. That keeps every replay of a committed credential on the socket's replay path. There is no `OUTPUT_REUSED` check any more; the code `bnap:notes/OUTPUT_REUSED` is reserved and never sent.

### Settlement (section 7)

- change = `value - charged`; charged is 0 on FAILED, so FAILED refunds the whole value (fees kept).
- The outputs must form a complete power-of-two ladder covering the value (6.3, checked at verify as `BAD_OUTPUTS`).
- `select(outputs, change)`: greedy by amount descending, then index ascending. Proven exact on complete ladders (brute force over 942 ladders, 55,542 targets, zero failures).
- DLEQ with NUT-12's deterministic nonce is a MUST, so settle is byte-deterministic.
- The signed-output table (NUT-09) must be durable no later than the outcome write. It is keyed by `(B', source)`, where the 32-byte source is `H(pay body)` of the credential that settled the output, or `rk_mint`, and it keeps every record. A `B'` signed before is signed again and gets its own record, never a settle failure. Records with the same keyset, amount and `B'` hold the same `C'` and DLEQ proof (NUT-12's nonce depends on `a`, `A`, `B'`, `C'` only), so NUT-09 answers with any record whose keyset, amount and `B'` match.
- NUT-04 minting (8.5) still refuses outputs signed before, but checks inside its transaction and only after recognizing a retry of the same mint request (`used[RailId] = rk_mint`).
- Timeout refunds are computed lazily when the client replays the credential (7.5). The gate must support "outcome FAILED, no scheme_result yet" and fill it with one conditional write.
- **Admission cutoff** (5.4, P9). Draft-00 4.4 answers STALE before the commit can find a replay, so a replay after the offer's deadline never reaches `outcome[rk]`. A notes gate therefore commits a new notes credential only until `cutoff = min(expires, quote_expires) - pending_timeout - 60 s`, checked inside the commit transaction after the replay lookup: an existing outcome is still served, a new commit past the cutoff aborts with STALE and consumes nothing. The socket `commit` needs an optional `admit_until` argument for this (owner of `bnap-plug` / the store crates). The gate MUST NOT list `bnap:notes` in an offer whose cutoff is less than 60 s after issuance; with `pending_timeout` 300 s, notes offers live at least 7 minutes (10 or more recommended), and the next route offer is issued before the current one's cutoff. Wallets replay unanswered credentials at once, at each `retry_after`, and when `pending_timeout` has passed, always before the deadline.

### Issuer and store requirements that cross crate boundaries

- **NUT-04 minting commits the RailId** (8.5) in the gate's use store, keyed `rk_mint = H_"bnap:notes/mint"(lp(quote ID) ‖ BigSize(k) ‖ lp(output₁) ‖ …)`, in one transaction with the signed-output records, with no outcome record and no PENDING state. The `UseStore` trait needs a single-ID insert-or-compare for this (the socket `commit` is not the right shape). Owner of `bnap-plug` / the store crates: please expose one.
- **NUT-23 quote state is derived from the use store** (8.6): issued exactly when the RailId is committed.
- **Quote retention** (8.6, P25): `verify` reads the quote record and asks the `ln` rail to confirm the payment on every verification, replays included. The issuer keeps a quote record (amount, `pubkey`, payment hash, paid state) exactly as long as its RailId record, and when a credential commits the RailId, keeps both until at least 60 s after that credential's notes deadline (`min(expires, quote_expires)`). The gate either stores that time with the RailId at commit (store crates: an optional per-ID retain-until) or keeps every redeemed quote for the longest notes offer lifetime plus 60 s. The `ln` rail plug must confirm the payment as long, answering from the quote record's paid state if the Lightning node prunes settled invoices. Without this, a replay of a funded credential gets `QUOTE_UNPAID` and loses its stored response, receipt and timeout refund.
- **NUT-07** answers from the use store; **NUT-09** from the signed-output table (12.2).
- **Retention after final expiry** (10): a note still verifies until its keyset's `final_expiry` plus 60 s, because draft-00 section 2's skew applies to every expiry check (6.2 step 2). Single-use records and signed-output records are kept until `final_expiry` plus 60 s, never deleted at `final_expiry` itself (ERRATA row 51).
- **Key isolation** (4.2): refuse NUT-03 swaps and NUT-05 melts of BNAP-keyset inputs.
- **Funding inside the 402** (section 8): the `BNAP-Fund` request field (RFC 9651 Dictionary: `amount` Integer, `pubkey` String of 66 hex characters). At most one quote per offer nonce, per-address rate limit, never without the field, `fund_quote` only in exact-scope offers.
- **Swap route**: manifest route id `notes-swap`, price `{"sat": 0}`, answered by the gate itself (section 11).

### Wallet requirements (section 15, 12)

NUT-13 derivation for version-01 keysets with type `0x02` for the note key and `0x01` for the blinding factor; 64-bit counter, top 16 bits = device slot; never reuse a counter; record the highest counter per keyset and slot in the backup at least every 100 values; restore in batches of 100, stop after three empty batches but never before the recorded counter. TLS binding: a wallet SHOULD bind whenever it can read `tls-exporter` and MAY retry unbound after a BINDING error (section 15, P30); v0.4's "agents and native clients MUST bind" is weakened because draft-00 5.3 makes gates behind a TLS-terminating front reject bound credentials (section 19.1 row).

### Test vectors

Section 18 lists what the notes vectors must contain. The socket vectors cannot serve as notes vectors: their route offer's `bnap:notes` pay entry has no `params` record (no `issuer`, no `keysets`, which notes 5.1 requires), so every input fails 6.2 step 2 with `UNKNOWN_KEYSET`, and its `expires`, 300 s after the reference time 1791700000, leaves no admission window under notes 5.4. The notes vectors therefore use their own **notes route offer** (notes 18.1): the socket route offer under the same offer key, MAC key, nonce, attest entry and GREASE record, with `expires` 1791703600 and a `params` record (issuer `https://api.example/cashu`, keyset A active with `input_fee_ppk` 100 and `final_expiry` 1830000000, keyset B inputs-only with fee 0 and `final_expiry` 1800000000; keys `a` = SHA-256("bnap notes test keyset L m") for m = 1 to 2^15; NUT-02 version-01 IDs). It is 413 bytes, OfferID `666b28f7f1d68d92e9c180f0d11fe743730d3932ab5bc566d68f53b17b0cbd95`; `nuts/tools/notes_offer_vector.py` regenerates it and checks that the same records without `params` and with the socket `expires` reproduce the socket OfferID `5c8640…`. Notes vector items 2, 3, 4 and 6 are built on it, and so is every negative vector of item 9 but one. `vectors/vectors.json` itself needs no change: its placeholder notes body tests socket hashing only.

Item 9's "fees above the inputs" (`BAD_AMOUNT`, fee > I + F) cannot be built on keysets A and B (repair round 4): k inputs on A pay at most (100k + 999) div 1000 ≤ k ≤ I, and a brute force over every mix of 1 to 16 inputs finds no case. It uses the **fee offer** of notes 18.1 instead: the notes route offer with a third keyset entry, keyset C (`input_fee_ppk` 2000, `final_expiry` 1830000000, not active, keys by the same rule with label `C`), ID `01fd899e9c7a7f4940273d43ec1dcd3bafc9fe4fe80ba292b9f021ab09b5aecf46`. Its entry adds 40 bytes (35-byte `id` record, 4-byte fee record, 1-byte length prefix), so `params` is 106 + 40 = 146 bytes and the offer 413 + 40 = 453, OfferID `b958c89e56ef83bb05dd98e88b0a4746f79ebac53c09c53f306e74635be1f2aa`. One 1-sat input on C gives fee (2,000 + 999) div 1000 = 2 > I + F = 1. The same tool prints it and now also asserts the published OfferID of the notes route offer.

Items 3 and 6 pin their amounts (repair round 3), because the earlier item 6 asked for an OK outcome with charge equal to the value for a two-input credential, which cannot exist. With the Web Bot Auth discount, `price(amount)` = 2,100 − ⌊2,100 × 2,000 / 10,000⌋ = 1,680. A no-change outcome needs value = 1,680, so two inputs would have to sum to 1,680 (both on keyset B, fee 0) or 1,681 (any on keyset A, fee (100 + 999) div 1000 = 1 or (200 + 999) div 1000 = 1); 1,680 has four bits set and 1,681 five, and a sum of two powers of two has at most two. A brute force over every pair from 2^0 to 2^15 on A+A, A+B and B+B finds none. The targets now are:

## 4. Decisions made

All 34 provisional decisions are listed in Appendix B of the notes document (P1 to P34), one row for every "(provisional)" marker in the text. P1 to P31 are numbered in section order. Repair round 1 renumbered them, and repair round 2 inserted P25 (quote retention, 8.6), which moved the old P25 to P30 up by one; the old numbers are gone. From P32 on, numbers are never reassigned: repair round 3 appended P32 (7.3) and P33 (2.1) instead of renumbering, so P1 to P31, P25 included, keep the meaning they have had since round 2. Repair round 4, the first follow-up round, appended P34 the same way. The ones with the widest effect:

- P2: unknown records in a notes body are rejected even when odd (draft-00 5.1 canonical bodies).
- P9: admission cutoff, so that every committed notes credential can still be replayed when its timeout refund is due (ERRATA row 50).
- P11: `verify` reads no use state; the v0.4 `OUTPUT_REUSED` check is dropped and the code reserved (ERRATA row 49).
- P12: one output ladder replaces v0.4's separate change and refund lists, because the charge of a metered call is known only at settlement.
- P15: outputs are not use IDs; the RailId alone guards fund quotes.
- P24: NUT-04 minting of BNAP keysets requires a NUT-20 key and commits the RailId.
- P25: a quote record lives as long as its RailId record, and both, with the rail's confirmation of the payment, last at least until 60 s after the deadline of the entry that committed the quote, so replays of funded credentials verify.
- P27: NUT-13 derivation type `0x02` for note keys is unassigned upstream.
- P32: in `scheme_result`, Required records are written even when empty (index 0 is `00 00`), empty optional records are left out, and clients read an absent index as 0 (ERRATA row 52).
- P33: a non-minimal BigSize or tu64 inside a notes body or witness is BAD\_CREDENTIAL with `bnap:notes/NON_CANONICAL`, not socket MALFORMED (ERRATA row 53).
- P34: on a route listed with `"scope": "route"`, a gate MAY also send a per-request exact-scope notes offer that carries a `fund_quote`, reading draft-00 9.1 as the route's default offer set (ERRATA row 55).

## 6. Known gaps

- The notes test vectors themselves (section 18) are not produced here; a reference-code owner must generate them, built on the 18.1 notes route offer. Items 3 and 6 now fix their amounts, keysets, metered counts, charges, signed indices and `scheme_result` sizes (section 1 above), so the generated bytes have targets to meet.
- Draft-00 8.1 requires `metered_units` in every Response to a metered offer but does not say what a FAILED action reports; notes vector 3a FAILED uses 0. The socket text, or the HTTP carrier together with ERRATA row 43, should say.
- The NUT-02 version-01 keyset ID layout was checked against the NUT-02 text and the cashu 0.18.1 test ID `015ba18a…`; NUT-02 itself publishes no version-01 test vectors.
- ERRATA rows 35 to 54 (section 5) still need merging into `spec/ERRATA.md` by the orchestrator, which owns that file.
- The NUT-13 derivation layout in 12.1 was taken from the current NUT-13 text and must be checked against its test vectors before the notes vectors are frozen.
- BOLT12 funding (NUT-25) is only mentioned, not specified for redemption inside a credential.
- Withdrawal (BNAP-W) is out of scope, as in v0.4.
- The I-D has not been rendered by xml2rfc yet; the first CI run may report warnings (for example typographic quotes from kramdown's smart quotes in table cells that had to leave code spans).
- The NUT drafts use relative links (`00.md`) that resolve only inside cashubtc/nuts.
- `UseStore` needs a single-ID insert-or-compare for NUT-04 minting (section 1 above); without it the issuer cannot follow notes 8.5.
- The socket `commit` needs an optional `admit_until` time, checked after the replay lookup, for the notes admission cutoff (notes 5.4, P9); without it a notes gate cannot guarantee timeout refunds under draft-00 as written. ERRATA row 50 would make it unnecessary.
- Quote records and their RailId records need a retention time set at commit (notes 8.6, P25), or the gate keeps every redeemed quote for the longest notes offer lifetime plus 60 s; the `ln` rail plug must confirm a quote's payment for as long.
- Downstream code written against the first version of this draft must drop the `OUTPUT_REUSED` check from `verify` and key the signed-output table by `(B', source)` (notes 6.2, 7.4).
- Downstream code written before repair round 3 must write the index of output 0 as the present empty record `00 00` and read an absent index as 0 (notes 7.3, P32), and must answer a non-minimal BigSize or tu64 inside a notes body or witness with BAD\_CREDENTIAL and `bnap:notes/NON_CANONICAL`, never MALFORMED (notes 2.1, P33).
